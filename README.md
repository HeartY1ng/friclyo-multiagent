# friclyo-multiagent

**本地备好 API 和 agent 框架，用的时候按任务自取。**

[English](README.en.md) · [改动记录](CHANGELOG.md) · [设计思路](docs/思路.md) · [切词实战](docs/案例/2026-10-13-切词实战.md)

> 项目名是 **friclyo**（v0.3.1 起；原名 frclyo）。命令、代码目录 `bin/frclyo/`、环境变量 `FRCLYO_*`、钥匙串条目 `frclyo-*` 等内部标识沿用 frclyo 前缀，不影响使用。

在本机准备模型资源池，让大脑按任务类型、难度和验收方式，选择“框架 × 模型 × 档位”。大脑负责定契约、派活和验收，工人负责交付，看板展示有证据的状态。

**第一版只支持 macOS，使用 Python 3.9+ 标准库和系统 bash。** 大脑范围为 Claude Code、Codex；工人范围为 Codex、OpenCode，后者连接 DeepSeek、Kimi、MiMo、GLM（国际编程套餐 Z.AI Coding Plan，`zai-coding-plan`；智谱国内按量付费，`zhipuai`）等 API。具体型号和档位需要实际校准，不保证任意组合可用。

```text
你 → 大脑（Claude 或 Codex）→ 账本
                                ↓
              工人（Codex、OpenCode 接 DeepSeek / Kimi / MiMo / GLM (Z.AI Coding Plan / Zhipu AI)）
                                ↓
                   回执 → 验收 → 看板
```

账本保留任务号、轮次和状态；执行结束不等于验收通过。看板展示进度，交付物仍须独立检查。

## 三条原则

1. **先定契约再拆活。** 先写清接口、格式、文件归属和坏输入处理，再决定是否并行；强耦合的活默认不拆。Cognition 的案例说明，各自合理的隐含决定也会造成集成冲突；契约是本项目据此采用的工程方法。[出处：Don’t Build Multi-Agents](https://cognition.ai/blog/dont-build-multi-agents)
2. **工人自述不算证据，靠回执和复跑验收。** 收齐产物后过契约关、一致关和端到端关；能写参考实现就做逐字节比较。MAST 将任务验证问题列为多 agent 失败的一类；回执机制和三关检查是本项目的应对方式。[出处：MAST](https://arxiv.org/abs/2503.13657)
3. **每件活能追溯、能撤销。** 用任务台账、进度台账和独立轮次目录留住事实，验收后才并入项目。台账借鉴 Magentic-One；安装登记、按账卸载和撤销边界是本项目的设计，不是论文已经证明的功能。[出处：Magentic-One](https://arxiv.org/abs/2411.04468)

## 三步上手

先安装并登录 Codex，或准备 OpenCode 及提供商 API。并行演示需要 Codex（可派两位工人），或 Codex + OpenCode；只有 OpenCode 时需两家提供商。框架不替你全局安装 CLI 或登录账号。OpenCode 首次使用前，在工人外运行 `opencode models --refresh` 准备本机模型缓存。

克隆仓库后进入目录：

```sh
git clone https://github.com/HeartY1ng/friclyo-multiagent.git
cd friclyo-multiagent
```

1. 安装：

   ```sh
   ./install.sh
   ```

   安装器检查环境并自动补齐工作目录布局；配置、命令链接、Claude 技能及看板自启分别确认，新增目录会登记。将 `~/.local/bin` 加入 PATH 后可运行 `aw`；安装器会提示缺少 PATH 的情况，也可直接使用 `./bin/aw`。

   安装器不生成 `配置/偏好.md`。启用大脑前，由用户将仓库 `偏好.模板.md` 复制到数据根 `配置/偏好.md`，填写并确认个人选择。偏好不是运行配置，模板示例不构成授权。

2. 登记 API：

   ```sh
   aw key add deepseek
   ```

   确认后由 macOS 钥匙串工具隐藏输入；密钥不进入对话、项目文件或安装记录。

3. 运行演示：

   ```sh
   aw demo
   ```

   确认组合与费用后，两个工人并行完成 CSV 规范化和分类汇总，核对回执后自动跑三关：样例逐字节、双方测试复跑、端到端逐字节。演示使用独立来源 `DM`，不占用 `CX` 编号。当前演示只检测配置端口是否监听；已有监听即按看板复用并尝试打开，尚未校验服务身份。端口被其他程序占用时不会启动临时看板；无监听时启动临时看板，演示结束后停止，可运行 `aw board start` 再查看。

数据根由 `FRCLYO_HOME` 指定，默认 `~/AgentWork`。配置位于 `$FRCLYO_HOME/配置/config.json`；新文件不存在时兼容读取 `~/.frclyo/config.json`，`aw doctor` 提示迁移，不自动搬运。测试才使用 `FRCLYO_CONFIG` 覆盖配置文件。旧字段 `work_dir`、`cards_dir`、`perf_file` 只警告并忽略，所有数据路径从根目录推导。Codex 文件优先读取 `CODEX_HOME`，未设置时才读取 `~/.codex`。密钥按配置的外部钥匙串条目、默认条目 `frclyo-<家>` / `frclyo`、显式配置的 `key_env_file` 依次查找；未配置外部条目时公开版默认行为不变。`aw key list` 改为每家一行显示来源（包括无可用 key），钥匙串只检查条目是否存在，不读取密码。Codex 模型清单优先查询本机 `codex app-server`，失败才回退共享缓存；缓存与实际 CLI 版本不同时仅供候选发现，不作为执行拦截依据。列出不代表实跑已验证；`aw doctor` 离线列出候选，看板未启动只显示 ⚠️，不影响退出码。`aw doctor --live` 经费用确认后按工人各选一个组合实跑。`aw calibrate` 对候选模型各选一个默认档位跑三题，不代表所有档位均已测试。用量保留回执原始对象，费用未知就留空。

可在配置中添加可选 `keychain_entries`，复用已有条目，例如：

```json
{
  "keychain_entries": {
    "deepseek": {"service": "my-deepseek", "account": "me"}
  }
}
```

家名必须在 `providers` 中；`service`、`account` 必须是非空字符串，不含控制字符且不以 `-` 开头。钥匙串每层仅在退出码 44（条目不存在）时继续查下一层。其他错误、超时或读取空值均停止回退；`get_key` 返回 None，并向 stderr 输出固定补救提示，建议在弹框里点“允许”或解锁钥匙串，不输出凭据。存在性查询遇到错误或超时显示“无法确认（钥匙串锁定或拒绝访问）”，不算可用 key。

`aw key add` 只写默认条目；外部条目存在或无法确认时拒绝添加，请用原工具更新，或先移除该家的 `keychain_entries` 配置。默认条目无法确认时也拒绝写入。来源为回退文件时可正常添加，并提示“当前从回退文件读取；存入钥匙串后优先用钥匙串”。默认条目已存在且由本工具登记时，提示先运行 `aw key remove <家>`；未登记时提示用“钥匙串访问”或 security 命令手动处理。`aw key remove` 和卸载仅删除本工具登记且尚未撤销的默认条目，保留外部条目、未登记默认条目和回退文件。

`aw key list` 的格式示例（假名称与路径，不含密码）：

```text
deepseek：钥匙串（外部）：my-deepseek（账户 me）
moonshotai-cn：钥匙串（默认）：frclyo-moonshotai-cn（账户 frclyo）
xiaomi：无可用 key
zai-coding-plan：无可用 key
zhipuai：无可用 key
```

其他状态示例：`deepseek：回退文件：/example/legacy.env`、`deepseek：无法确认（钥匙串锁定或拒绝访问）`。list、doctor 模型发现和看板没有余额接口的存在性检查均不读取钥匙串密码；余额请求本身仍需读取凭据。来源存在不保证凭据可读或有效。

模型可用性保存在 `$FRCLYO_HOME/模型可用性.json`，按工人、模型和实际 CLI 版本记录状态、UTC 时间及原因。候选按 `ok`、`unknown`（未测）排序，`unusable` 默认隐藏；运行时接口 `models.discover(include_unusable=True)` 可返回全部候选，每项含 `availability` 和 `cli_version`。CLI 版本变化后，旧版本结论不参与本次选择，旧记录保留；版本查询失败也按未测处理。

`aw demo`、`aw calibrate` 和 `aw doctor --live` 遇到明确的模型不支持错误时，在同一工人的剩余候选中自动切换，最多换 3 个（含首选共 4 次），每次使用新轮次并保留失败证据。OpenCode 可以切到另一家已登记的提供商，演示会避开另一位仍在运行的工人占用的提供商。普通网络、鉴权、超时、回执或产物验收失败不会触发切换。正常执行记 `ok`，与产物评分分开；模型支持错误记 `unusable`，其他失败不覆盖既有可用性结论。并发读写加锁，文件原子替换。

演示三关通过返回 0，执行或验收失败返回非零。校准完成出报告后返回 0，即使存在失败组合；`路由建议.md` 列出失败原因、轮次和证据路径，不能仅看退出码判断模型质量。真实自检按各工人的最终验收结果返回 0 或非零。记录按 CLI 版本区分，不保存账号身份；同版本后续成功记录可以覆盖旧的不可用结论。

### 日审与回执例外

日审只读核对账本里“完成·通过”的卡。只有 `r数字` 轮次时，仍按数字大小核对最新一轮（例如 `r10` 晚于 `r9`），最新数字目录缺回执也会报错。命名轮次的名称只能含英文字母、数字、`-`、`_`，不能以 `-` 开头，且目录内须有 `回执.json` 或 `运行信息.json`；普通资料目录不算轮次。卡内只要有命名轮次，就逐轮核对全部轮次，包括数字轮次。每轮的任务号、轮次号、执行完成状态和结果 SHA-256 必须一致。有问题时按卡计数，显示“共 N 轮，其中 k 轮有问题：轮次名（原因）…”，最多列 5 个问题轮次，更多时末尾写“等”。没有轮次的总卡仍按子卡收卡状态处理。

大脑已核对交付并完成宿主验收，但回执未反映结果时，可在收卡时登记原因：

```sh
aw ledger 完成 <任务> --结论 通过 --摘要 "已核对交付与宿主测试" --回执例外 "回执收尾失败，宿主测试已通过"
aw ledger 回执例外 <任务> "回执收尾失败，交付物及宿主复跑已核对"
aw ledger 查 <任务>
```

第一条在同一次账本追加中先写 `回执例外：原因` 备注，再写完成事件；未收卡也可用 `aw ledger 备注 <任务> "回执例外：原因"`。备注必须以全角冒号的 `回执例外：` 开头，原因必须有实质文字。第二条用于补登，所有已开卡任务（含已完成、已放弃）均可登记，未知任务拒绝；不必为补登恢复卡片。英文别名为 `done --receipt-exception`、`receipt-exception`、`show`。

补登写到账本同目录 `回执例外.jsonl`，每行包含 `时间`、`任务`、`原因`，采用账本相同的 UTC 秒级时间（如 `2026-11-01T10:00:00Z`）、锁、追加和落盘机制，不改账本字节、事件格式或状态规则。单独文件用于回滚兼容：已结束任务再追加普通账本事件会被旧版判为损坏；旧版会忽略独立文件，因而旧日审也不会识别仅在此文件中的例外。

日审合并两种来源，选同一任务时间最新且原因非空的一条；同秒优先独立文件，同一来源同秒取最后一条。空原因不清除已有说明，普通备注不覆盖例外。独立文件坏行跳过并提醒行号，其余记录照常处理。`aw ledger 查` 展示有效记录及「账本备注」或 `回执例外.jsonl` 来源。

**回执例外只豁免回执／交付证据类问题，不豁免“总卡下子卡没收”。卡被恢复重新打开后，之前登记的例外不适用于之后的新轮，登记时已有的轮次仍被豁免。专用命令（`完成 --回执例外`、`回执例外`）登记时会记下当时已有的轮次清单，只豁免清单里的轮次；没有清单的旧记录按时间判断，同一秒不豁免。** 例外保留历史，不改变任务状态、不改回执，也不替代产物验收。证据正常仍显示成功；适用的证据问题显示 `⚠️ 回执例外已说明：原因` 并保留任务及原问题，不计入问题数。JSON 放入 `提醒`；没有其他问题时日审退出 0。看板显示灰色“回执例外已说明”（“有空看看”），不列为“要紧”或要求再次决定。

### 新建任务卡

`aw 卡 新建 找bug CL-20261101-05` 从账本已开卡任务生成 `$FRCLYO_HOME/任务卡/CL-20261101-05-r1.txt`。模板可选 `找bug`、`修复`、`改动审查`、`实验`，也接受对应 `…卡.md` 文件名；项目和默认标题来自账本，`--标题` 与 `--轮` 可覆盖标题及轮次。命令只生成待填草稿，不派活、不改账本、不登记执行轮次，目标已占名就拒绝。

轮次名不能为空，只能包含英文字母、数字和 `-_`，且不能以 `-` 开头。建卡、派活与执行入口采用一致约束。

### 批量派活

```sh
aw 派活 队列.json --试跑
aw 派活 队列.json --并行 3 --额度上限 95
# 英文入口及选项同义：
aw dispatch queue.json --parallel 3 --quota-limit 95 --dry-run
```

队列是 JSON 列表，例如：

```json
[
  {"任务":"CL-20261101-01","工人":"codex","模型":"gpt-6-astra","档位":"high","超时":7200},
  {"任务":"CL-20261101-02","轮":"r1","工人":"opencode","模型":"deepseek/实际可用的模型名","变体":"","超时":1800}
]
```

请替换为已在账本开卡且尚未收卡的真实任务与本机可用模型。`轮` 默认 `r1`；`卡` 默认 `任务卡/<任务>-<轮>.txt`；`输入` 默认 `素材/<任务>`。这两类路径相对 `$FRCLYO_HOME`，也可显式指定绝对路径；没有素材时请准备空输入目录。Codex 的 `网页`、`命令网络`、`子agent`、`快速档` 接受 `0/1` 或布尔值，全部默认关，覆盖继承环境。现有 OpenCode 入口不支持开启这些开关，传入开启值会整批报错。

预检还包括字段、路径和任务状态；试跑不查实时额度、不改账本。默认总并行 3，同一家 OpenCode 在同一数据根的派活批次间串行，直接调用工人脚本不参加锁。周额度按 10080 分钟窗口识别，读数不可用或窗口不可识别时该 Codex 项失败且不启动；停派阈值不是硬性消费封顶。逐项结果仍写 `<批次号>.jsonl`，stdout/stderr 另存独占 `.log`；派活只记账本备注、不收卡。全部完成或试跑通过退出 0，执行失败／额度跳过退出 1。

`aw 派活 队列.json --试跑` 与正式派活均在启动整批前校验模型和档位。Codex 使用本机命令行 `model/list` 返回的可见模型及其支持的思考档位，不用 App 缓存代替命令行清单；OpenCode 使用当前工人配置的模型白名单和显式变体，与框架现有模型发现逻辑一致，禁用变体不接受，空串表示默认变体。每种工人的清单每次预检只读取一次。清单不可读时给警告、继续其他校验，不据此拦截；列在清单中不等于已实跑验证可用。错误指出队列中的项号，整批返回 `2`。Codex `ultra` 仍须同时开启 `子agent=1`。

本机 Codex CLI 为 `0.153.x` 时，`子agent=1` 只允许 `gpt-5.6-luna`。其他模型的 exec 子 agent 已知会报 `no thread with id`，其中 astra 还可能伪报成功；派活校验及 `codex-worker.sh` 启动检查均拒绝该组合，返回 `2`。显式环境变量 `CODEX_WORKER_SUBAGENTS_FORCE=1` 可以跳过这项版本兼容性防护，仅用于试新版本；它不跳过模型、档位或 ultra 开关校验。其他 CLI 版本以及无法识别的版本不按此规则拦截。这个开关不替代任务卡中的拆分授权。

Codex 在开工前或结算完成后任一次有效周额度读数达到上限，本批后续 Codex 均停止补派；周额度随后重置也不解除本批停派。已开工的工人自然完成，OpenCode 继续调度。

Ctrl-C 与 SIGTERM 均停止补派，等待已启动的工人和监督器自然结束，然后写齐逐项日志、汇总并返回 `130`。队列 JSON 语法错误返回 `2`；文件访问或配置、账本运行故障仍返回 `1`。

正式批次新增 `运行时/派活/<批次号>.批次.json`。开始时原子写入：

```json
{
  "批次号": "20261101-120000-0123456789ab",
  "开始时间": "2026-11-01T20:00:00+00:00",
  "总件数": 2,
  "并行数": 3,
  "额度上限": 95,
  "任务": [
    {"任务": "CL-20261101-01", "轮": "r1"},
    {"任务": "CL-20261101-02", "轮": "r1"}
  ]
}
```

结束时原子补入 `结束时间`（UTC ISO 8601）及 `结束状态`，状态为 `完成`、`被中断`、`校验失败`。`完成` 表示调度已收尾，批内仍可能有失败或额度跳过项；逐项结果以原有 JSONL 为准，不代表验收通过。校验失败的正式调用只写批次信息，不写逐项 JSONL、不启动工人；无法解析的队列总件数记 `0`、任务列表为空，可解析列表中的无效任务号／轮次类型记 `null`。试跑不写批次信息，也不创建运行目录。没有结束字段表示尚无结束记录，不能仅据此断定进程仍在运行（强制终止或存储故障也可能缺少结束记录）。原 `<批次号>.jsonl` 每行字段和含义保持不变。

### 复现交付测试

```sh
aw 复现 <任务> <轮> --框架 输入
aw 复现 <任务> <轮> --框架 交付
aw 复现 <任务> <轮> --框架 /路径/框架-开发
aw 复现 <任务> <轮> --框架 交付 --不套沙箱
```

`--框架`（`--framework`）默认 `输入`，测试这一轮的 `输入/框架`；`交付` 测试这一轮的 `交付/框架`；其他值是相对于调用目录的目录路径，也支持绝对路径。命令先复制轮次的 `输入/`、`交付/`，指定路径另复制到本次临时目录的 `指定框架/`，再运行复制后的 `交付/复现测试/test_*.py`。复制时跳过 `.git` 和 `__pycache__`，其余符号链接和特殊文件仍拒绝。指定树缺失时明确失败，不回退到输入树。

`FRCLYO_REPRO_ROOT` 与兼容变量 `REVIEW_SOURCE`、`REVIEW_REPO`、`AW_REVIEW_REPO`、`REVIEW_FRAMEWORK`、`FRCLYO_REVIEW_ROOT`、`REPRO_FRAMEWORK` 全部指向所选框架的临时副本。测试应从该变量加载框架；写死输入路径的旧脚本需要适配。输出显示源目录和原版／修复版；`交付` 和目录路径均按“修复版应全部没复现”汇总，退出 1 的测试显示“仍复现”。显式指定输入树的目录路径也按修复版口径显示。

默认仍通过 macOS `sandbox-exec` 运行，禁止联网，写入只开放临时副本和 `/dev/null`。只有显式给出 `--不套沙箱`（`--no-sandbox`）才直接启动 Python；运行前显示“测试代码将直接在本机运行”。该模式没有本命令施加的网络／文件沙箱限制，请核对测试内容后使用。沙箱不可用时不会自动切换。无沙箱模式仍保留复制、干净环境、300 秒总限时（含兼容重试）、中断及后代进程收尾、独立日志。TMPDIR 仍须位于用户 HOME 和原轮次之外。

每个脚本退出 1 表示复现，退出 0 表示没复现，其余退出码表示测试本身出错。普通异常、`FAIL`、`ERROR` 等输出不覆盖退出码。例外：非零退出且输出中出现行末诊断 `sandbox_apply: Operation not permitted`（可带 `sandbox-exec:` 前缀；支持行首或 `AssertionError: … :` 等冒号后的格式）时，归为“环境受限：沙箱不能嵌套”，提示显式加 `--不套沙箱` / `--no-sandbox` 重跑，不进行缺模块兼容重试。成功退出中的同样文本不改变判定。超时、启动失败、未确认收尾仍优先报执行错误；环境受限、跳过或准备失败都不能证明已修复。

`--测试`（`--test`）精确选择文件名，可省略 `.py`。缺少 `frclyo` 模块时，仍从副本的 `交付/` 兼容重试一次；两次合计 300 秒。日志保存在 `$FRCLYO_HOME/运行时/复现/<任务>-<轮>/run-<随机标识>/`：`results.json` 是逐项结果数组，`run.json` 记录源目录、临时框架路径、沙箱模式和预期；完整输出在 `<测试文件名>.attempt-N.log`，沙箱模式另有 `sandbox.sb`。

命令自身退出 0 表示收集完成，可能仍含“复现”或“仍复现”；退出 1 表示准备错误、测试本身出错或环境受限；用法错误退出 2。修复验收须检查逐项结果全为“没复现”，不能只看命令退出码。

复现脚本必须自行捕获准备失败、导入失败和权限错误，以 0/1 以外的退出码（例如 2）报告；unittest 默认把失败和错误都记作退出 1，不能据此区分。判定遵循测试契约，不独立证明测试正确。`--测试` 不解释通配符。

日志名含 `.attempt-N.log` 后缀；总 UTF-8 长度不超过 240 字节时沿用 `<测试文件名>.attempt-N.log`。超过上限时使用 UTF-8 边界安全的截短前缀、连字符、原测试文件名的完整 SHA-256 十六进制摘要，再加尝试后缀，完整日志名仍不超过 240 字节。每次尝试单独保留日志；`results.json` 的 `test` 保留完整原名，`attempts[].log` 记录实际日志文件名。

超时、中断或正常结束都复用执行监督器的后代快照与多轮回收，包含已记录的独立会话后代；无法确认回收时保存错误诊断。快照机制沿用现有监督器的限制：两次采样之间生成并脱离的后代可能漏记，不能把它描述为内核级进程容器。

复现测试编写约定见[任务卡模板](docs/协议/模板/任务卡.md#复现测试产物与自检)。

### 合并工人成果

```sh
aw 合并 <任务> <轮> --到 /路径/框架-开发 --试跑
aw 合并 <任务> <轮> --到 /路径/框架-开发
```

`aw 合并` 把一轮完整工人交付合入开发版。默认基准为 `$FRCLYO_HOME/素材/<任务>/框架/`，工人交付为 `$FRCLYO_HOME/交付/<任务>/<轮>/交付/框架/`。先用 `--试跑` 看清单；权限处理见下文。双方改动以 `git merge-file` 三方合并，冲突文件不写入，其他无冲突文件可继续应用。所有写入的 Python、Shell 文件经过语法检查，失败则回滚本批写入和删除。

`--并集 bin/tests/test_example.py` 可显式保留双方新增的测试方法；此选项可重复，支持 `.py`、`.sh`，以及首行 shebang 可识别为 Python、bash 或 sh 的无扩展名脚本（含 `bin/aw`）。无扩展名识别接受直接解释器路径或 `/usr/bin/env`（含 `-S`），限 `python`、`python3`、`python3.N`、`bash`、`sh`；Shell 沿用 `bash -n`，不执行 shebang 中的程序。删除默认只提醒；加 `--允许删除` 才删除未在开发版另行修改的文件。用多个 `--只许 'bin/tests/*'` 指定允许范围并单独提醒范围外改动；它是提醒，不是过滤器。退出 1 可能表示部分无冲突文件已合入，必须阅读清单。合并到同一目录应串行执行；不支持链接、特殊文件或文件/目录互换的自动处理。

权限提示以工人该轮实际收到的 `$FRCLYO_HOME/交付/<任务>/<轮>/输入/框架/` 为比较依据。输入副本与交付文件都是 0600 时，不会因为开发版或素材基准具有可执行位而逐文件报“工人权限改变”。只有交付权限与输入中同一文件的权限不同才逐项提示，并汇总“工人改了 N 个文件的权限”，包括 N 为 0 的情况；同时改内容和权限也会计数。已有开发版文件仍保留开发版权限，新增文件仍沿用交付权限；新增文件没有输入权限可比较，不计为 chmod。`--基准` 只选择内容三方合并的基准，不改变权限比较来源。缺少本轮 `输入/框架/` 时，在写入前报“需要输入”，应补回该轮实际输入副本，不应以开发版或素材权限代替。

同一卡、同一轮、同一份交付重复执行 `--并集` 时，若对应冲突块已经包含完整、连续的工人代码块，就保留该块，不重复追加。合并结果与开发版完全相同时，不重写文件，内容、权限和修改时间保持不变。写入前还会核对候选结果重跑是否稳定；相邻删除等无法稳定合并的文件明确报冲突并保留开发版，需人工处理。该处理按冲突位置比较，不对全文件逐行去重，保留不同位置或块内部有意重复的代码。并集仍不保证业务语义正确，合并后必须复跑相关测试。

`bin/aw` 的 bash/Python 双语言包装按开闭边界识别，不再要求 `exec python3` 启动行与旧文本完全相同；加入 `-B` 等参数后仍分别检查 Python 全文和 Shell 启动前缀，不执行交付代码。

## 版本发布与回滚

框架支持运行中发布。稳定入口 `$FRCLYO_HOME/框架` 指向只读目录 `框架-版本/<完整提交号>`；工人启动时固定物理版本，后续发布不会改变它使用的脚本和模块。

首次启用需暂停派工、等已有工人退出，再用包含此功能的 `框架-开发/bin/aw 发布 --迁移` 导出当前稳定仓库。原仓库保留为 `框架.迁移前`。撤销为 `框架-开发/bin/aw 发布 --撤销迁移`，同样要求停派工。旧提交没有版本管理命令时，继续使用开发版入口管理。

```sh
aw 发布                 # 开发版 HEAD 必须干净，且已推至分支对应的本地文件远端
aw 发布 --付费验收      # 候选版本执行 aw 验收 --paid
aw 回滚                 # 切回上一次切换前的版本
aw 回滚 <完整提交号>
aw 版本                 # 当前、上一个、各版本工人数
aw clean                # 预览可清理的轮次和旧版本
```

英文命令为 `release [--paid]`、`rollback [commit]`、`versions`；迁移选项为 `--migrate` 和 `--undo-migration`。发布先验收候选再原子切换；验收失败不动稳定入口。发布、回滚、迁移和撤销会重启看板并记改动台账。

版本不会自动删除。清理沿用 `aw clean --yes` 的完整数据根路径确认，只允许清理无人使用、不是当前/上一个版本且有完整登记和启动锁协议的旧版本。进程查询不全时保留；从旧代码迁移而来的无锁协议版本也保留。不要手工改动只读快照。

### 失败恢复与版本状态

发布先验收候选快照，再切换稳定入口。切换之前失败，原入口保持可用；撤销迁移恢复目录失败时，会补回原版本链接。当前版本目录已丢失时，可从开发版入口执行 `框架-开发/bin/aw 回滚 <完整旧提交号>`，目标必须完整且已经登记验收。

切换之后，状态写入、完成台账或看板重启失败，命令非零退出，并说明“版本已切换”和失败步骤。保留已验收的新入口与 `pending`，修复故障后再运行 `aw 发布` 即可补做收尾；这次补做不会重新验收开发版，也不会把上一版覆盖成自己。迁移和撤销迁移也可用原命令补做。进程在切换之前中断，会先恢复原入口或清掉未完成的切换记录，再重试原操作。

快照已改名但登记失败时，同一提交可重发：重新导出、验收，确认现有只读快照与新候选指纹相同后补登记。内容不同或目录不再只读时保留目录并报错。被杀遗留的 `.candidate-*` 目录会在下一次取得发布管理锁时清掉，例如下一次 `aw 发布`。旧版本删除先持久化删除意图；删除或完成台账中断后，`aw clean` 显示“继续中断的清理”，按原有完整路径确认流程继续删除。当前、上一版、正在使用或存活状态未知的版本仍受保护。

`aw 版本` 保留“当前 / 上一个 / 旧版本”和工人数，增加“发布时间”和“残缺/不可回滚”及原因。目录缺失、内容/权限改变、未登记、未验收或正在清理均不可回滚。版本损坏标记本身不改变列表命令退出码；进程扫描或使用记录整体不可用时仍非零退出并禁止清理。未知发布时间显示“未知（旧记录或尚未切换）”；使用记录无法确认存活时另行标明未知。

补做记录采用至少一次语义：某一步完成、但其进度标记落盘前进程被杀，重试可能重复记录完成台账或再次重启看板。稳定入口与已完成的版本仍保留。

显式 `aw 回滚 [完整提交号]` 优先于未完成的发布收尾；不能因旧发布的收尾失败而阻止用户要求的回滚。

版本时间与工人使用记录字段见[运行目录与边界](docs/运行目录与边界.md#版本元数据与工人使用记录)。

## 卸载

```sh
./uninstall.sh --dry-run
./uninstall.sh
# 也可使用 aw uninstall
```

按 `$FRCLYO_HOME/配置/安装记录.jsonl` 撤销：先确认本工具登记的 launchd 服务已停止，再按记录逆序撤销其他安装项（命令链接、Claude 技能和本工具新增的钥匙串条目）；服务未确认停止时保留其依赖文件。修改过的安装文件会保留。未指定 `--delete-data` 时，默认和 `--yes` 保留配置、安装记录及工作数据；`--yes` 会确认撤销安装项（含本工具登记的钥匙串条目）。只有 `./uninstall.sh --delete-data`（或 `aw uninstall --delete-data`），并再次逐字输入规范化的根目录完整路径后，才会先按本数据根的交付索引清理满足安全条件的根外私有临时目录（Codex `.frclyo-work` 及 OpenCode 非 ASCII 根回退目录），再递归删除数据根；根外节点无法安全清理时保留根目录和索引。`--yes` 不能代替此确认；错误路径、EOF、`--no-input`、`--dry-run` 均不删。无安装记录、撤销失败、危险根路径或符号链接路径会保留。备份须同时覆盖数据根内所有内容及上述根外节点；真实根下包含框架时也在删除范围内。外部旧配置和凭据回退文件不会顺带删除。

根目录不能是 git 仓库，也不能位于文稿、桌面或 iCloud。安装器只补齐缺失的 `配置/`、`框架/`、`框架-开发/`、`任务卡/`、`交付/`、`素材/`、`项目/`、`运行时/opencode/`、`运行时/控制/opencode/`（以及必要父目录）、`台账/备份/`、`台账/归档/`；不克隆版本、不生成大脑入口或主人的 README。账本旧卡片字段 `runs/xxx` 在内存视图映射到根内 `任务卡/xxx`，历史事件字节不变。

## 安全默认

- **守则注入**：仓库 `工人守则.md` 全文先于任务卡写入本轮 `任务.txt`，回执保存启动前捕获的 `守则sha256`；不依赖交付父目录的规则文件。
- **文件隔离**：两种工人都拒绝账本、配置、其他轮交付及宿主控制目录。OpenCode 只额外开放本轮运行时/临时目录、只读模板和快照，并限制数据根外用户数据内容读取；Codex 保留根外一般读取范围，敏感路径仍拒绝。交付只写本轮，另有本轮私有状态/临时目录与 `/dev/null` 写例外；实际边界须经宿主探针验证。
- **工人断网**：Codex 命令执行默认断网，网页搜索按任务显式开启；OpenCode 使用 macOS 沙箱禁止直接出网。
- **反向代理**：OpenCode 仅连本轮随机回环端口的 HTTP 接口；宿主代理向固定本家 HTTPS 主机与路径添加 Bearer 认证，丢弃客户端认证头，不提供 CONNECT，不跟随跨主机重定向。不放行工人直接外联、DNS 或其他回环端口。
- **钥匙串**：OpenCode 提供商 key 由宿主读取，经匿名管道交给反向代理；工人进程没有真 key，模板仅含固定占位值。支持 `deepseek`、`moonshotai-cn`、`xiaomi`、`zai-coding-plan`、`zhipuai`；可配置 `keychain_entries`，用 `aw key list` 查看来源。Codex 使用宿主 CLI 登录；框架不改用户 Codex 或 Claude 配置。
- **零遥测**：框架不上传使用记录、任务、表现或统计。模型请求和看板额度／余额查询会连接相应服务，第三方 CLI 自身行为受其配置及政策约束。
- **可撤销**：机器变更先确认并记账，工人按独立轮次交付；看板只读且只监听 `127.0.0.1`。每小时日审核对账本中“完成且结论为通过”的任务，按[日审与回执例外](#日审与回执例外)规则选择轮次、核对回执与结果哈希；无轮次父卡按子卡收卡状态判定。

回执哈希只覆盖结果说明，完整产物正确性仍靠复跑验收；日审不代表整机安全审计。OpenCode 模型目录必须来自本机缓存，启动器不自行下载。

## 每轮目录、限额与排障

交付保存在 `$FRCLYO_HOME/交付/<任务>/<轮>/`；OpenCode 状态在 `运行时/opencode/rounds/<任务>/<轮>/`，宿主可信捕获在 `运行时/控制/<工人>/<任务>/<轮>/`。纯英文临时目录：OpenCode 默认 `$FRCLYO_HOME/tmp/…`（根含非 ASCII 时回退），Codex 在数据根外的宿主 `.frclyo-work/…`（必要时回退）。轮次目录默认保留；确认进程组已回收、产物和证据已留存后，可运行 `aw clean [--days N]` 预览已收卡且有可信退出证据的私有目录；`--yes` 仍需输入数据根完整路径。交付目录、账本和不满足安全条件的节点不会由该命令删除。精确路径、保留建议和 Codex 根外临时文件可读的限制见 [运行目录与边界](docs/运行目录与边界.md)。

输入通过 `WORKER_INPUT_DIR` 注入，默认总大小 1 GiB、文件和目录条目合计 10000，可由宿主用 `WORKER_INPUT_MAX_BYTES`、`WORKER_INPUT_MAX_FILES` 调整；拒绝输入内部链接和特殊文件，失败写“准备失败”回执并停止。结果默认 16 MiB，可用 `WORKER_RESULT_MAX_BYTES` 调整；工人 stdout/stderr 合计固定 64 MiB。公开日志在轮结束且确认进程组回收后才发布，运行中证据在宿主控制目录。OpenCode 调试使用 `OPENCODE_WORKER_DEBUG=1`。

工具操作遵循 [工人守则](工人守则.md) 第 3 条及末尾约定：Codex git/构建在入口 `$TMPDIR` 的工作子目录完成再拷回；Swift、OpenCode `mktemp -p "$TMPDIR"` 等具体做法见守则，不自行替换环境或在拒绝后重试。

## 看板与项目

账本未登记的轮次，运行时显示“进行中”；结束后显示灰色“测试”（`TEST-` 前缀）或“未登记”，失败带后缀，不因这些测试结果进入“要你处理”。同时运行多个项目时，正在干活区按项目分组并标明负责对话；项目色固定。

可选项目表 `$FRCLYO_HOME/配置/项目表.json` 将项目映射到负责对话，例如：

```json
{"项目": {"示例项目": {"负责对话": "框架维护"}}}
```

缺失或损坏按空表处理，负责对话显示“未登记”；看板“怎么办”提示发往相应对话，不自动发送消息。

### 版本与派活

“版本与派活”面板继续展示全部项目的数据。桌面上左侧为版本、右侧为最近五批派活；窄屏改为上下排列，批次和版本列表展开状态在刷新后保留。

有 `运行时/派活/<批次号>.批次.json` 的批次显示队列总件数、开始时间、结束时间及结束状态。完成、失败、跳过数量来自逐项 JSONL 结果；“额度跳过”和“被中断”的逐项结果计入跳过。批次无结束记录时，“在跑”按总队列中尚无结果的项数计算，包含待启动项，不能据此认定进程还活着。只要已有结束字段，“在跑”即为零；批次状态“完成”仅表示调度收尾，不等于每项成功或验收通过。“被中断”“校验失败”保留原状态显示，尚无结果的项标明“无结果（已结束）”。仅有批次 JSON、没有 JSONL 的批次也能展示。

旧批次无元数据时，总数仍显示未知；在跑只提供已关联运行轮次的至少数，未发现时显示未知。元数据损坏、逐项结果不完整或读取达到上限时，不把不足的证据当作精确在跑数，并显示提示。token 合计只统计已知用量。

当前版本以稳定入口为准。当前版本与最多十条版本记录的发布时间只采用 `published_at`，缺失显示“未知（旧记录）”，不从文件修改时间或 `prepared_at` 推测。列表纳入只读版本接口发现的未登记/残缺版本；版本完整性、可回滚状态、清理状态和原因由 `version_rows(root)` 提供。版本列表仍为有界展示，不是完整版本清单。

“还在用旧版本的工人”只列 `worker_usage(root)` 返回 `active is True` 且完整提交号不同于当前版本的登记，显示工人、任务、轮次、PID 和版本。`active is False` 不列入；`None` 单列“无法确认”。当前入口未知时，也不能判断活跃登记是否属于旧版本。使用记录读取失败或超时，两个工人列表均显示“未知”，不显示零或空登记结论。旧启动器可能没有登记，因此空登记列表不能证明旧版本无人使用；锁文件存在也不能证明占用。

看板每三秒刷新页面数据，两个发布只读接口分别异步读取并缓存三十秒（失败也缓存），单次读取限三秒。首次读取和缓存过期刷新期间显示“正在读取，未知”；异常或超时只影响相应信息，不阻塞其他看板数据。使用记录可比真实进程状态滞后三十秒左右；该面板不提供发布、回滚或清理操作。

## 验证

```sh
python3 tests/run_all.py
```

一次运行 `bin/tests`、`board/test_board.py` 和 `tests` 全部必过离线测试；零测试、失败和跳过都返回非零。测试使用临时 HOME、假钥匙串和假模型，不消耗 API 费用。CI 在 macOS 的 Python 3.9、3.13 上调用同一入口。

宿主各脚本须单独运行并记录退出码，完整清单见 [宿主验收入口](tests/host/README.md)，边界与判定见 [隔离验收](docs/隔离验收.md)。`sandbox_doctor.py`、`runtime_rounds.py`、`proxy_credentials.py`、`test_proxy_tcp.py` 和默认 `network_check.sh` 不调用真实模型；部分会启动临时本地服务。`isolation_check.sh --offline-only` 因未做两项真实复述，预期整体退出 1，不能写成完整通过。

完整 `isolation_check.sh`、`codex_tmp_smoke.py` 和 `network_check.sh --live` 会调用真实模型，产生 API 用量或消耗订阅额度。OpenCode 走宿主钥匙串与反向代理，不再要求把 `DEEPSEEK_API_KEY` 注入环境。各入口的钥匙串配置、模型缓存和 CLI 依赖略有区别，运行前按宿主说明准备。离线测试不能替代内核与真实模型验收。

### 验收被中断

`aw 验收`（`tests/host/verify_all.py`）及离线测试入口 `python3 tests/run_all.py` 收到 SIGINT / Ctrl-C 或 SIGTERM 后停止启动后续检查，收尾已启动的进程组及已采样的后代进程，包括另开会话的后代。已有检查结果保留，当前检查及汇总标记“被中断”；SIGINT 返回 130，SIGTERM 返回 143。收尾期间再次收到信号，不改变第一次信号对应的退出码。

验收证据仍写在 `--output` 指定位置或数据根的 `运行时/验收/`。离线测试入口在系统临时目录下新建 `.offline-evidence-*`，打印“证据目录：”；逐组保存 `output.log`、`result.json`，并保存 `summary.json` / `summary.txt`。该证据目录独立于测试使用的临时 HOME，测试结束后保留；宿主验收会按原有证据协议汇集日志与 JSON 汇总。

后代回收复用 `bin/frclyo/execution.py` 的 PID 与启动时间快照，需要允许系统进程查询。快照失败或不能确认全部回收时明确记失败，不报告通过。该机制沿用现有采样边界：两次采样间产生并脱离父系的进程可能漏记，不是内核级进程容器；SIGKILL 无法捕获。需要完整验证时，在具备进程查询权限的宿主运行 `python3 -B tests/test_b131_interruption.py`。

## 和现成工具的区别

本项目选择保留自己的执行、契约和验收体系，有限投入只读看板。输入对比报告中的 Vibe Kanban 更侧重工作区、diff 审查和 PR 开发流程；codex-orchestrator 更侧重 Codex 持续会话、追问和终端调度。这些能力各有价值，本项目优先处理多模型派活和独立验收，尚未实现与它们的即插即用桥接。[比较范围与出处](docs/案例/工具对比.md)

对比来自一次静态快照审阅，不是性能排名。网络隔离实现和主机验收脚本已随仓库提供；发布前仍须完成主机实测。回执哈希只覆盖结果说明，不能证明所有产物完整或正确。[设计与边界](docs/思路.md)
